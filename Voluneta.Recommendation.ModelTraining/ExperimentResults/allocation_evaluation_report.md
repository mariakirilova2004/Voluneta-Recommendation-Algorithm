# Allocation Algorithm Evaluation Report (Algorithm 2)


## Configuration

- Algorithms compared: `MinCostMaxFlowPriorityAllocator` (existing optimal allocator) vs `GreedyPriorityAllocator` (existing baseline)
- Thresholds evaluated: 0.30, 0.50, 0.70
- Both algorithms are run on identical candidate pairs, compatibility scores, cause capacities, and thresholds for each scenario (fresh capacity instances per run).
- Scenarios: 1 hand-authored educational case + 3 deterministic synthetic cases with varied volunteer/cause counts and capacities, generated from fixed random seeds.

## Important: constructed test data, not neural network predictions

All compatibility scores and capacities used in this evaluation are **constructed test fixtures**:

- The *Educational Greedy vs Optimal* scenario uses the same hand-authored scores as the Optimization demo's educational example (`DemoEducationalScenario`), deliberately chosen to make the Greedy vs Min-Cost Max-Flow trade-off easy to see.
- The *Synthetic* scenarios use scores and capacities generated by `System.Random` with a fixed seed, so each run is reproducible but the scores do **not** come from the trained neural network and do not represent real volunteer/cause compatibility.
- This report only evaluates allocation (Algorithm 2) behavior given some scores; it does not evaluate neural network prediction quality (see `neural_evaluation_report.md` for that).

## Methodology

For each scenario, the same candidate list and equivalent cause capacities are passed to both
allocators at each threshold (0.30, 0.50, 0.70). Scenarios are built once with a fixed seed (where
applicable) so results are fully reproducible across runs. For each algorithm/scenario/threshold
combination, four metrics are recorded from the resulting `RecommendationPriorityResult`:

- **Prioritized volunteer count** - `PrioritizedCount`, the number of volunteers given a priority recommendation.
- **Total compatibility score** - `TotalScore`, the sum of compatibility scores across all selected pairs.
- **Average selected compatibility score** - total score divided by the prioritized count (0 when nothing is selected).
- **Capacity utilization** - prioritized count divided by the scenario's total remaining capacity across all causes.

## Min-Cost Max-Flow vs Greedy: how to read the results

`MinCostMaxFlowPriorityAllocator` solves a min-cost max-flow problem: it first **maximizes the number
of assignments** (flow), and only among solutions achieving that maximum assignment count does it
minimize total cost (equivalently, maximize total compatibility for that cardinality). `GreedyPriorityAllocator`
instead picks the best-scoring pairs first without this cardinality guarantee.

As a result, when both algorithms select the **same number** of volunteers, Min-Cost Max-Flow's total
compatibility score is guaranteed to be greater than or equal to Greedy's for that scenario/threshold.
However, **when the two algorithms select different numbers of volunteers**, their total scores are not
directly comparable this way: Min-Cost Max-Flow may select more volunteers at a lower total or average
score per volunteer, because it is optimizing assignment cardinality first. This report does not claim
that Min-Cost Max-Flow's total compatibility must always exceed Greedy's; the measured counts and totals
below should be read together, not the total score alone.

## Limitations

- Scores in all scenarios are constructed test fixtures (educational or seeded-random), not real neural network predictions or real volunteer/cause data.
- Only 3 synthetic scenario sizes and 1 educational scenario are evaluated; results may not generalize to all candidate pool shapes.
- Capacity utilization is defined relative to total capacity across causes, not per-cause utilization.
